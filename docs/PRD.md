## Local wishlist extension (source base `42100cc`)

The local extension supplies two read tools and freshness metadata. - `flighty_get_tracking_status({flight_id})` resolves an exact eligible cached UUID, including owner passenger/followed and cached shared non-owner passenger memberships in Flight/ManualFlight. Exclude deleted/unlinked rows and other users' follows. Return all associations with `tracking_source` (`owner_passenger`, `owner_followed`, `cached_shared_passenger`), unverified friendship, name provenance and ambiguity. A Profile is not verified friendship or proof of travel. Keep unknown followed passenger names and `friend_name: null`; never use the owner's name as that passenger. Preserve per-association booking attribution.
- Derive runway landing countdown from valid estimate, then labelled schedule; gate ETA is separate. Expose calculation time and field bases, overdue/null without inferred touchdown, cancelled/unknown states and timestamp diagnostics. Actual gate departure means taxi-out, runway departure airborne, runway arrival taxi-in, gate arrival at-gate. Taxi elapsed/completed durations are cached milestone calculations, not live surface progress. Legacy status keeps gate fields, adds phase/reason and supports `taxi_out`/`unknown`; `in_air` requires runway departure and `landed` includes touchdown.
- `flighty_check_connection({inbound_flight_id,outbound_flight_id})` requires distinct UUIDs and eligible membership on both legs in one snapshot. Pair is proposed; traveler identity is not established. Gate layover uses chronologically validated actual/estimated/scheduled bases, retains negative margins, and uses null for missing evidence. Reject contradictory current predictions rather than silently adopting a stale schedule. Use only exact ordered pair MCT with matching known transfer-airport context. Unknown/conflicting MCT and missing/invalid tails remain null. Cancellation, invalid milestones, airport mismatch, negative margin, below MCT and meets-cached-MCT states need honest reasons. Boarding cutoff and walking/security/immigration remain unknown. No same-person or safe-connection guarantee. The legacy `flighty_get_connections` remains an owner-passenger scheduled list; prefer the explicit-pair tool for followed/shared risk checks.
- All results, including empty/error/validation, carry server-authored local `queried_at` and freshness metadata without weakening trust/error/owner handling. `queried_at` is invocation/early-error handling time, not exact snapshot or sync time. `last_synced_at` and ages stay null for unknown numeric `SyncInfo.lastSync` epoch/units, invalid/future/missing markers, mixed unknown formats or bounded-scan overflow. Only a complete safely parsed marker set can supply its chronological maximum. Scope is database-level, never an identified account or per-flight freshness guarantee; the exact scope literal is `database_sync`. About/reference/error paths must not add sync/owner/credential access. Keep volatile timing/freshness outside removal preview hashes.
- No true refresh or new API use. Re-querying only rereads committed cache. Background helpers may update it without a visible window; Mac cadence and individual-flight freshness are not guaranteed. No verified live aircraft telemetry source: `cruising_speed_kmh` is static specification and airport coordinates are not plane position.
